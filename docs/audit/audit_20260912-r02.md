## The most important new bug: semaphore deadlock

The V1 decision to force `maxConcurrentJobs = 1` is correct and fixes the earlier single-tab race.

But the semaphore implementation is now wrong.

When a job gets the slot immediately:

```ts
this.#activeJobCount += 1;
```

When another job waits and is awakened, its callback **also increments** the count:

```ts
this.#activeJobCount += 1;
```

But releasing a slot to a waiter does not decrement the previous owner's count:

```ts
const next = this.#concurrencyWaiters.shift();
if (next) {
  next();
} else {
  this.#activeJobCount = Math.max(0, this.#activeJobCount - 1);
}
```

So:

```text
A starts        active = 1
B waits         active = 1
A finishes
  wakes B       active still 1
B callback
  increments    active = 2
B finishes
  no waiter
  decrements    active = 1

No job is running, but active == maxConcurrentJobs.
C arrives and waits forever.
```

Your concurrency test doesn't catch this because it runs A+B, verifies sequential execution, and destroys the fixture. It never submits C afterward.

The simplest fix is to treat wake-up as **slot transfer**:

```ts
const onSlotAvailable = (): void => {
  signal.removeEventListener("abort", onAbort);
  resolve();
};
```

Do not increment `#activeJobCount` there.

Then add a regression:

```text
A and B overlap
await both
submit C
C must complete
```

I would fix this before anything else.

## The connector/repository capability guarantee still isn't real

You corrected the capability definition itself. It now requires:

```text
chatgpt-access
adviser-model
github-connector
target-repository
```

That's exactly what I recommended.

But the actual `advisor_preflight` production tool still only calls `resolveCheckpoint()`. That verifies local git + GitHub REST availability of the SHA; it does **not** verify ChatGPT's GitHub connector or whether ChatGPT can read that repository.

Likewise, normal submit goes from:

```text
checkpoint resolution
→ engine
→ Project/conversation
→ model discovery
→ ChatGPT turn
```

without evaluating `REQUIRED_BEFORE_FIRST_CONSULTATION`.

This means the core failure mode remains possible:

```text
SHA is definitely on GitHub
ChatGPT is definitely signed in
strong model is available
BUT ChatGPT GitHub connector is absent/disconnected

→ adviser receives repo + SHA in prose
→ cannot inspect code
→ produces plausible generic advice
```

That is particularly dangerous because provenance headers can still look valid.

I would introduce one authoritative production method, something like:

```ts
ensureConsultationCapability(repository, checkpoint)
```

and require it from both explicit preflight and dispatch. A cached successful capability result is fine, provided repository visibility/connectors have sensible invalidation.

## `firstVisible()` still has a concrete live-DOM bug

The driver comment says it handles the common ChatGPT case where a selector matches many nodes and the first is hidden.

The scan does find a visible `nth(index)`, but returns `locator`:

```ts
if (await locator.nth(index).isVisible().catch(() => false))
  return locator;
```

Callers then do:

```ts
picker.first()
composer.first()
send.first()
```

So suppose:

```text
selector match 0 = hidden mobile composer
selector match 1 = visible desktop composer
```

`firstVisible()` confirms #1 exists, returns the collection, and the caller then operates on hidden #0.

That precisely defeats the robustness mechanism the comments describe.

The Project-surface implementation already uses the better pattern: return the actual element. I would change the Playwright helper to:

```ts
Promise<AdviserElement | undefined>
```

and:

```ts
return locator.nth(index);
```

Then remove `.first()` from downstream calls.

The current driver tests cover stale answers, missing composers, selector injection, health checks, and operation locking, but not “first match hidden, later match visible.”

Add that regression because real ChatGPT DOMs commonly have hidden duplicate responsive controls.

## There is still a cancellation/completion race

The store correctly implements first-terminal-winner semantics:

```ts
if (isTerminalJobState(current.state)) return current;
```

So if cancellation wins just before completion, `store.complete()` returns the already-cancelled record.

But the engine success path assumes that `complete()` necessarily completed the job.

After:

```ts
const completedRecord = await this.#store.complete(...)
```

it immediately writes a ledger entry with:

```text
status: "completed"
```

and persists the adviser answer.

Race:

```text
browser answer finishes
engine checks abort → false

                     cancel arrives
                     job → cancelled

engine calls complete()
store returns existing cancelled record

engine nevertheless writes COMPLETED ledger entry
```

Then `readPersistedResponse()` is likely absent, so the engine follows another failure branch, but the job store and ledger can now disagree.

### Fix

Immediately inspect the returned terminal state:

```ts
const terminal = await store.complete(...);

if (terminal.state !== "completed") {
  return outcomeForExistingTerminalState(terminal);
}
```

Better still, make the API explicit:

```ts
{ won: true, record }
{ won: false, record }
```

Then only the winner may produce success-side ledger effects.

This deserves a deterministic test with a test hook/barrier just before `store.complete()`.

## Session isolation is improved, but `taskId` reintroduces a hole

Slash commands now correctly use:

```ts
ctx.sessionManager.getSessionId()
```

for task identity. That fixes the earlier `"session-default"` problem.

The agent tool, however, allows:

```ts
taskId = requestedTaskId ?? sessionId;
```

So two Pi sessions can independently call:

```text
advisor_submit(taskId="review", kind="review")
```

against the same repository.

Both then get the same ChatGPT conversation key even though response delivery keys remain different.

That's exactly the sort of context contamination INV-09 is supposed to prevent.

Use a composite identity:

```text
<pi-session-id>:<logical-task-id>
```

or hash the pair.

A worker-provided logical task ID can still be useful, but it should never replace the session namespace.

## The production composition root has a subtle multi-workspace race

The new lazy composition root is a major improvement.

However:

```text
servicesByCwd:
  cwd A → Engine A
  cwd B → Engine B

browser:
  one shared BrowserBundle
```

Each engine has its own:

```text
activeJobCount
conversationQueues
```

but both engines share the same Playwright runtime/project surface and therefore the same tracked tab.

Within one engine, max concurrency 1 protects:

```text
navigate A
→ send A
→ receive A
```

Across Engine A and Engine B, there is no common engine semaphore.

The driver serializes *individual* page operations, and the runtime serializes *turns*, but conversation navigation occurs through the Project surface outside that runtime turn queue.

So the original pattern can return across workspaces:

```text
Engine A: navigate conversation A
Engine B: navigate conversation B
Engine A: runtime.consult(prompt A)
```

### Fix

The browser should have exactly one process-wide transaction scheduler.

I would prefer:

```text
one BrowserBundle
one ConsultationEngine / browser dispatcher
many workspace request contexts
```

rather than an engine per cwd.

Alternatively put a shared browser-operation mutex around the entire:

```text
ensure/select conversation
+ model resolution
+ send
+ await
+ read
```

transaction.

This also avoids first-workspace browser configuration bleeding into subsequent workspace engines.

## Browser account identity is still not matched to Pi identity

You fixed the earlier false claim that Pi OAuth means the isolated web browser is authenticated. `adviserStatus()` now explicitly separates:

```text
Pi OpenAI sign-in
ChatGPT browser session
```

Good.

But the stronger identity machinery still isn't connected.

`SessionObservation` supports:

```ts
{ kind: "signed-in", identity?: AccountIdentityHint }
```

Yet the production Playwright adapter maps a signed-in ChatGPT page to:

```ts
{ kind: "signed-in" }
```

without identity.

And `/advisor-auth` therefore validates:

```text
Pi signed in
AND
browser signed in
```

but not:

```text
Pi account == browser account
```

So if the isolated profile contains another person's/work account, consultations proceed against that account.

Given the existing `auth/adviser-auth.ts` mismatch state machine, I would finish wiring that instead of introducing another comparison mechanism.

## Model selection works now, but `"auto-best"` isn't really “best”

The previous `"chatgpt-default"` bug is fixed.

But the new default is:

```ts
DEFAULT_MODEL_PREFERENCE = ["auto-best"];
```

There is no special `auto-best` handling.

Since no ChatGPT model is literally named `auto-best`, resolution falls through to:

```ts
const fallback = selectable[0];
return {
  degraded: true,
  reason: "no preference available; used most capable selectable model"
}
```

Two problems:

1. `selectable[0]` is merely **first in DOM/menu order**, not demonstrably most capable.
2. Default use will normally be recorded as **degraded every time**, because `"auto-best"` never matched.

And model discovery itself currently relies heavily on the first locator's text rather than robustly iterating all visible options.

I would model this as an explicit policy:

```ts
type ModelPreference =
  | { mode: "best-available" }
  | { mode: "ranked"; models: [...] };
```

Then `"best-available"` succeeding should be `degraded: false`.

But determining “best” needs either an explicit rank table or a trusted UI semantic—not raw DOM position.

## Recovery/ledger work is much better

These parts passed the re-audit well.

You now have:

* durable lookup by consultation ID;
* real cancellation using the persisted address;
* startup reconciliation of stale `running` jobs to `failed/interrupted`;
* terminal failed/cancelled jobs projected into ledger history;
* atomic ledger rewrites;
* malformed non-tail JSONL records rejected;
* cross-repository ledger enumeration implemented;
* lock wait extended to accommodate browser reconciliation.

One remaining integrity issue is that `normalizeLedgerEntry()` still casts many arbitrary JSON values into branded/enumerated types without validating them:

```ts
resolvedCommit: obj.resolvedCommit as FullCommitSha
status: (obj.status ?? "completed") as DurableJobState
kind: (...) as ConsultationKind
```

and notably:

```ts
const schemaVersion =
  typeof obj.schemaVersion === "number" && obj.schemaVersion === 1
    ? 1
    : 1;
```

So any schema version becomes v1.

That's worth tightening, but unlike before, it isn't a normal crash-loss hazard.

## Async mode works mechanically, but “wake-up” is mostly UI notification

The async engine and session-scoped listener are now actually wired. That's another major improvement.

Completion currently does:

```text
ctx.ui.notify(...)
```

It does not inject the advisory into Pi's model context or trigger/resume an agent turn.

So from the worker's perspective:

```text
advisor_submit async
→ receives "queued"
→ keeps working
→ adviser completes
→ human UI gets notification
```

The worker only sees the actual advice after somebody invokes `advisor_read` or another turn causes it to fetch status.

That may be entirely acceptable for V1, but I would call the feature **asynchronous notification**, not full **agent wake-up/delivery**, unless you subsequently inject a session-scoped custom message.

The protocol documentation itself notes that results remain available for explicit status/read and that live browser verification remains manual.

---

## Cancellation still has weak operational semantics

Cancellation now correctly changes durable state and doesn't fake success. Good.

However, the browser turn itself doesn't consume an `AbortSignal`. Engine cancellation therefore marks the job cancelled, but `runtime.consult()` can continue waiting for the ChatGPT generation until its full timeout. The single V1 browser slot remains occupied meanwhile.

With a 240-second configured timeout, this UX can be:

```text
Cancel
→ UI says cancelled
→ next adviser request sits waiting several minutes
```

Don't release the slot and immediately reuse the tab while ChatGPT is still generating—that would recreate correctness problems. Instead plumb cancellation into the Playwright polling/turn layer and either stop generation safely or reset the page once generation has conclusively stopped.

## Recommended fix order

1. Fix the **semaphore slot leak** and add the A+B→C regression.
2. Fix the **completion/cancellation winner race**.
3. Make browser transaction serialization **global across all cwd-specific engines**, or collapse to one dispatcher.
4. Fix `firstVisible()` and model-option enumeration.
5. Put the four-item **capability gate on the actual dispatch path**, especially ChatGPT GitHub connector + repository visibility.
6. Namespace tool `taskId` by real Pi session.
7. Finish **Pi-account ↔ browser-account identity validation**.
8. Give `auto-best` explicit semantics and ranking.
9. Harden ledger schema validation.
10. Improve cancellation propagation, cross-process browser ownership, and async worker delivery.

After 1–7, I'd be much more comfortable calling this **release-candidate quality**. I would then run a small live-browser canary matrix before tagging it: fresh profile, already-signed-in profile, disconnected GitHub connector, private/public repo, two overlapping async consultations, cancellation during generation, two repositories in one Pi process, and two Pi processes contending for the adviser profile. The repository's own docs correctly acknowledge that live ChatGPT/browser round trips are still manual verification territory, so that is now the largest test gap rather than the unit-test architecture itself.
