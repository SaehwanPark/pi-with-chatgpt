I would **not treat the current `main` as production-ready yet**, despite the architecture being much stronger than a typical first implementation. The internal modules are thoughtfully separated and many safety invariants are implemented well, but several integration defects mean the installed Pi extension can currently **claim that ChatGPT advice happened when ChatGPT was never contacted**, and some provenance/concurrency guarantees do not hold on the real Pi execution path.

I reviewed the current repository source, Pi-facing integration, git/checkpoint path, browser/runtime, project/conversation mapping, job engine, ledger, auth, drift, and release tests. I could not independently execute the full suite in this environment, and importantly the repository currently has **no active GitHub Actions workflow**: the intended CI file is parked under `ci/` rather than `.github/workflows/`. The repository itself documents why.

The first six are the ones I would fix before doing further feature work.

## 1. P0: the actual Pi extension does not wire the implementation together

This is the most important issue.

The default Pi entry point creates:

```text
CommandManager(...)
ToolManager(...)
```

but doesn't construct a `ConsultationEngine`, adviser browser/runtime, Project surface, job store, or login adapter.

Both managers therefore run without an engine during normal Pi installation. The tool path explicitly has an **“Offline stub”** branch that writes a fabricated completed consultation into the ledger and returns `ok: true`.  The slash-command path similarly creates a fake response and reports completion when `this.engine` is absent.

That yields the worst possible failure mode for this project:

```text
user asks ChatGPT for review
        ↓
no ChatGPT request happens
        ↓
extension returns successful adviser result
```

The tests don't catch it because the higher-level release tests explicitly inject `makeMockEngine(...)`; the activation smoke test mainly verifies registration counts.

### Fix

Keep activation itself cheap and side-effect free, which is a good design choice, but introduce a **lazy production service container**:

```text
activate()
  ↓
register commands/tools only
  ↓
first adviser operation
  ↓
getServices()
    ├─ load config
    ├─ initialize state
    ├─ create adviser profile
    ├─ create Playwright driver/runtime
    ├─ create Project surface
    ├─ create job store
    ├─ create ledger
    ├─ create engine
    └─ create auth/login services
```

Most importantly:

> **No-engine must be an error/unavailable state in production, never a fake adviser success.**

Keep a stub only in explicit test fixtures.

## 2. P0: checkpoint verification currently fails open

The GitHub-only checkpoint model is one of the strongest parts of the architecture, and `resolveCheckpoint()` itself is well designed: the exact commit's GitHub presence is treated as decisive, while local remote-tracking refs are explicitly advisory.

But the production GitHub adapter breaks that invariant.

When neither `GITHUB_TOKEN` nor `GH_TOKEN` is available, `defaultGitHubApi()` returns:

```text
checkCommitPresence()
  → { ok: true, value: "present" }
```

rather than an unknown/unverified result.

So:

```text
HEAD exists only locally
origin/main is behind
no GitHub token
        ↓
fake GitHub API says commit exists
        ↓
checkpoint becomes dispatch-ready
```

That defeats the foundational “ChatGPT must be able to inspect this exact SHA remotely” property.

### Fix

Fail closed:

```text
public GitHub repository
  → anonymous GET commit/SHA is acceptable

private repository + usable credential
  → authenticated exact-SHA verification

cannot verify
  → status: unknown / github-auth-failed / probe-inconclusive
  → no dispatch
```

Never substitute success for unavailable infrastructure.

This should get a dedicated regression test:

> **A local commit not on GitHub must never pass preflight when no GitHub credential is present.**

## 3. P0: Pi's real session identity isn't being used

Your local Pi API abstraction currently expects:

```ts
ctx.sessionId
```

But current Pi's actual `ExtensionContext` exposes:

```ts
ctx.sessionManager
```

and `ReadonlySessionManager` explicitly provides:

```ts
getSessionId()
```

The extension therefore falls through to:

```text
session-default
```

in normal command handling.

That's not just metadata loss. Your conversation scoping deliberately depends on task/session identity. If two Pi sessions working on the same repo both become `session-default`, they can be mapped onto the same adviser conversation.

### Fix

Make the Pi integration type match Pi rather than approximating it:

```ts
const sessionId = ctx.sessionManager.getSessionId();
```

And use that for:

* `taskId`;
* delivery-key derivation;
* async wake-up registration;
* conversation mapping.

I'd also add an integration test using a **real-shaped `ExtensionContext`**, rather than a test mock containing the nonexistent `sessionId` convenience field.

## 4. P0: parallel jobs can cross-send between conversations

The engine defaults to two concurrent consultations and serializes only jobs sharing the same conversation.

Meanwhile the Playwright driver deliberately owns a **single tracked page/tab**; its Project surface operates on that same page.

The engine sequence is effectively:

```text
job A:
  inspect/navigate conversation A
                        ↓
job B:
  inspect/navigate conversation B
                        ↓
job A:
  runtime.consult(prompt A)
```

The final `runtime.consult()` doesn't carry a conversation ID and therefore sends into whichever conversation the shared page currently displays.

The individual browser operations are serialized, but the **logical transaction**:

```text
navigate to A
+ verify A
+ send A
+ await A
```

is not atomic.

### Fix

For V1, I strongly recommend:

```text
maxConcurrentBrowserConsultations = 1
```

This costs very little because ChatGPT consultations are already heavyweight and avoids an entire family of race conditions.

Later, if parallelism matters, implement:

```ts
consultInConversation(conversationId, request)
```

where one browser lock encloses:

```text
navigate
verify URL/conversation
select model
send prompt
wait response
read response
```

Alternatively use one independently owned Playwright page per active conversation.

Do not advertise independent parallel adviser conversations until this is fixed.

## 5. P0: consultation identity is generated twice

The extension creates an `adv-...` ID before constructing the ChatGPT brief.

The engine then creates a durable job, and the job layer independently generates another consultation ID unless one is supplied.

But `EngineConsultationRequest` doesn't currently carry the preallocated consultation ID.

Therefore you can get:

```text
ChatGPT sees:
  CONSULTATION: adv-A

job store:
  adv-B

response parser expects:
  adv-B

UI initially announced:
  adv-A
```

This also makes follow-ups confusing: code creates a local `followUpId`, but the engine can persist another ID.

### Fix

Allocate exactly once.

I prefer:

```text
extension
  ↓
engine.prepareConsultation()
  → allocates adv-X
  → returns identity
  ↓
brief built with adv-X
  ↓
engine.submit(... consultationId: adv-X)
```

or simply let `submit()` accept a caller-provided `consultationId`.

One identifier must span:

```text
brief
job
conversation event
response
ledger
UI
follow-up
```

## 6. P0/P1: real model selection is implemented but bypassed

You already wrote a reasonable `resolveModelPreference()` abstraction supporting ranked preferences and explicit degraded fallback.

But command/tool submission hardcodes:

```text
modelId: "chatgpt-default"
```

The Playwright driver then tries to match that value against actual model-picker labels.

`chatgpt-default` is an internal-looking sentinel, not an actual ChatGPT model label, so after fixing the missing engine wiring the next likely result is:

```text
model-unavailable
```

### Fix

Have runtime do:

```text
listModels()
  ↓
resolveModelPreference(["preferred", ...], liveModels)
  ↓
select concrete returned model
```

For the `"auto-best"` case, don't invent a synthetic model ID.

If the current selected ChatGPT model is already acceptable, using it can be even more robust than interacting with the model-picker DOM unnecessarily.

## 7. Auth logic exists, but production UI bypasses it

`auth/adviser-auth.ts` is actually one of the better parts of the project. It correctly distinguishes:

```text
Pi OAuth identity
≠
ChatGPT browser authentication
```

and requires profile/capability/account verification before consulting.

But `adviserStatus()` primarily tells you whether Pi has OpenAI OAuth and whether the adviser profile directory exists.

The worker-facing `advisor_auth` then reports:

```text
authenticated = status.openAiSignIn.present
```

That is not the same as:

> isolated adviser browser is currently authenticated to ChatGPT.

### Fix

Make one production preflight pipeline authoritative:

```text
Pi OAuth identity
  ↓
isolated-profile existence
  ↓
ChatGPT access probe
  ↓
browser account identity
  ↓
model capability
  ↓
GitHub connector
  ↓
target repository access
  ↓
READY
```

`resolveAdviserAuth()` already gives you most of that state machine. Wire it rather than maintaining a simpler status path with looser semantics.

## 8. GitHub connector must be mandatory for V1

Your stated V1 architecture is:

> **GitHub is the sole repository-context channel.**

Yet the capability checklist explicitly omits `github-connector` from `REQUIRED_BEFORE_FIRST_CONSULTATION`, even commenting that an unverified connector should not block.

That means ChatGPT may receive:

```text
repo
SHA
question
```

but have no ability to read the actual code.

A strong model can still produce an excellent-looking generic review, potentially even echoing the requested SHA.

### Fix

For V1 require all four:

```text
✓ ChatGPT access
✓ adviser model
✓ GitHub connector
✓ target repo through that connector
```

I'd make first-use repository validation concrete: ask ChatGPT through its GitHub connector to retrieve some known repository fact at the target SHA.

The Project instructions themselves are good and correctly establish the authority ordering.

## 9. Cross-thread responses aren't rejected strongly enough

The response parser correctly checks `reviewed_commit`, and marks missing/mismatched SHAs as provenance ambiguity. That's good.

However, when the returned consultation ID disagrees with the expected consultation ID, it merely adds a parsing note. It does **not** degrade the result status.

That's especially risky given the shared-tab race described earlier.

If both jobs review the same SHA:

```text
job A response accidentally read from thread B
SHA matches
consultation ID differs
        ↓
currently still can appear complete
```

### Fix

Provenance should be the tuple:

```text
(repository, consultationId, reviewedCommit)
```

At minimum:

```text
missing/mismatched consultationId
  → provenance-ambiguous
```

For V1 I would probably be stricter and refuse to classify it as a clean completion.

## 10. Async architecture exists but isn't connected to Pi

The engine has useful async machinery:

* durable dispatch;
* async execution;
* wake-up listener registration;
* delivery-key isolation.

But extension activation registers no Pi lifecycle handlers.

And command/tool submission always calls `submitSync()` regardless of configured `defaultMode`.

So the implemented async layer is currently effectively unreachable through normal Pi use.

### Fix

Once real Pi context is adopted:

```text
session_start
  → sessionManager.getSessionId()
  → register wake-up listener

session change/shutdown
  → unregister listener
```

Then dispatch according to config:

```text
sync  → submitSync()
async → submitAsync()
```

For completed async results, use Pi's supported custom-message/follow-up mechanism rather than trying to mutate historical context.

## 11. Job store and adviser ledger need clearer authority boundaries

The durable job store is thoughtfully designed. It writes the job before dispatch, claims it transactionally, and persists the response separately.

But the user-facing status path mainly consults `ConsultationLedger`, while the engine only writes the ledger on **successful completion**. Failures and cancellations live only in the job store.

This produces cases such as:

```text
job running
Pi crashes
        ↓
job remains "running"
        ↓
not present in completed ledger
        ↓
/advisor-status may not see it
```

I also didn't find an implemented reconciliation path for ambiguous post-crash `running` jobs.

### Fix

Make the boundary explicit:

```text
JobStore
  = current operational truth
    queued/running/completed/failed/cancelled/interrupted

Ledger
  = immutable consultation history
```

Status should query JobStore first.

Every terminal transition should eventually produce a ledger event.

On startup:

```text
running from dead previous process
  → interrupted / reconciliation-needed
```

Don't automatically resend, because browser submission may already have occurred.

## 12. Cancellation currently cannot reliably target the job

`advisor_cancel` constructs an address using:

```text
taskId: "session-default"
deliveryKey: "000000..."
```

rather than loading the real stored job's immutable address.

The store correctly rejects scope mismatches, so the safety layer actually makes this fail—which is good—but the command then has poor semantics around success reporting.

There's another edge case: concurrency-slot acquisition can reject due to abort before the execution pipeline enters its main `try/finally`, which risks incomplete cleanup.

### Fix

Expose:

```ts
cancelByConsultationId(id, repo/session scope)
```

which first reads the persisted job and obtains its true `JobAddress`.

Never synthesize an address.

And structure slot acquisition as:

```ts
let acquired = false;
try {
  await acquire(...)
  acquired = true
  ...
} finally {
  if (acquired) release(...)
  removeAbortController(...)
}
```

## 13. Ledger mutation can destroy the ledger during a crash

Most of your state primitives are cautious: private permissions, symlink checking, temp files and atomic rename.

But `updateActionItemDisposition()` rewrites the JSONL ledger with a normal `writeFilePrivate()` call, even though the comment says it is an atomic rewrite.

For an existing file, that primitive uses truncation before rewriting.

A process crash here can therefore leave:

```text
consultations.jsonl = partially rewritten/truncated
```

The parser then compounds this by skipping malformed lines anywhere in the file instead of treating a corrupt middle line as an error.

Also:

```ts
#readAllRepositoriesLedgers()
```

currently just returns an empty array, so global ID lookup/list behavior is incomplete.

### Better design

I'd make dispositions append-only:

```text
consultation_created
consultation_completed
action_disposition_changed A1 implemented
action_disposition_changed A2 rejected ...
```

That fits your ledger concept better than rewriting historical records.

Otherwise, use temp-file + atomic rename and treat only a malformed **final** JSONL line as crash-recoverable.

## 14. “Read-only git” is not necessarily “no local code execution”

The git authority implementation is otherwise excellent: a narrow allowlist blocks mutation commands and dangerous flags.

But `git/exec.ts` itself documents an important residual risk: repository-local `.git/config` may define executable behavior such as:

```text
core.fsmonitor
diff.external
```

which some nominally read-only git commands can invoke.

This matters because `git status` runs during normal preflight.

### Fix

Two layers:

1. **Honor Pi project trust.** Current Pi exposes `ctx.isProjectTrusted()`.
2. Neutralize executable git config for adviser-owned inspection where feasible.

For example, explicitly disable fsmonitor/external-diff mechanisms or use invocation-specific safe config.

I'd make auto-consultation impossible in an untrusted project.

## 15. Remote choice should follow actual publication topology

Current selection is deterministic:

```text
origin
→ upstream
→ first GitHub remote alphabetically
```

Determinism is good, but in a common fork setup:

```text
origin   = upstream project
fork     = user's writable/pushed branch
```

the desired checkpoint may exist on `fork` but not `origin`.

You currently select first, then test presence.

### Better approach

Use git's actual push topology when available:

```text
branch.<name>.pushRemote
remote.pushDefault
branch.<name>.remote
@{push}
```

and/or probe all GitHub candidate repositories for the exact SHA.

If multiple contain it, then apply deterministic preference.

## 16. A few lower-level issues are easy wins

The default state-lock wait is 15 seconds while browser navigation can take 45 seconds, and Project creation intentionally holds the mapping lock across browser work. Two valid Pi processes can therefore produce `state-busy` under ordinary slow network conditions.

`isHealthy()` races `page.title()` against a three-second timer but doesn't inspect whether the timer won; a hung renderer still returns `true`.

Config defines meaningful options such as `defaultMode`, `syncTimeoutMs`, `pollIntervalMs`, `autoConsult`, and `browserExecutablePath`, but normal activation doesn't load user/project config and several options are not propagated into runtime behavior.

Also preserve detached-HEAD provenance: callers currently substitute `"main"` when `workingState.branch` is absent even though the durable record type already permits `null`.

These aren't architectural problems, just wiring/hardening work.

## One subtle issue with response secret scanning

After ChatGPT replies, the engine runs the generic credential detector across the **entire adviser answer** before persistence.

Patterns include things such as:

```text
sk-...
GitHub token shapes
Cookie: ...
private-key headers
```

That's good for preventing accidental browser-secret persistence, but ChatGPT may legitimately discuss a **fake/example token appearing in repository tests or security documentation**. In that case an otherwise valid audit can fail because its prose happens to contain a credential-shaped string.

I'd distinguish:

```text
local/browser credential material → must never persist

repository-derived adviser prose
→ redact sensitive-looking substrings
→ mark response as redacted
→ preserve rest of advice
```

rather than turning the whole consultation into a browser-like failure.

# What I think is already strong

There is quite a lot worth keeping.

The **checkpoint model is good**: requested ref and immutable full SHA are kept separate, availability has `available/unavailable/unknown`, and dispatch fails when the actual anchor isn't verified.

The **Project instructions are well designed**: repository-specific but free of mutable branch/SHA/task state, with checkpoint code correctly ranked above Project memory.

The **Project mapping code** is unusually careful about duplicate creation, corruption, rename/recreate semantics, locking, and preserving mappings under inconclusive network state.

The **browser profile isolation and filesystem permission work** are thoughtful, especially the ownership marker, 0700/0600 policy, and symlink refusal.

And separating ChatGPT's advice from execution remains intact architecturally. The main weakness isn't the conceptual design; it's that a number of sophisticated lower-level modules have not yet been connected coherently at the production composition layer.

## Fix order I recommend

1. **Remove all fake-success paths and build the production composition root.**
2. **Fail closed on GitHub SHA verification.**
3. **Adopt real Pi `ExtensionContext`/`sessionManager` semantics.**
4. **Make consultation ID allocation single-source.**
5. **Set browser consultation concurrency to 1 for V1.**
6. **Wire real model selection + auth state machine + mandatory GitHub connector verification.**
7. **Then make async mode/session wake-up operational.**
8. **Unify JobStore/ledger/status/cancel/recovery semantics.**
9. **Make ledger updates crash-safe.**
10. **Harden git execution against repo-local executable config and enforce Pi project trust.**
11. **Activate CI and add a production-wiring end-to-end test.**
12. Then address remote selection, lock timing, health checks, config completeness, and UX details.

My assessment is therefore **“excellent architecture, incomplete composition/hardening” rather than “bad implementation.”** I would especially avoid spending time on more features until items 1–6 are fixed: after those, the implementation should cross an important threshold from a well-tested collection of components into a trustworthy end-to-end adviser system.
