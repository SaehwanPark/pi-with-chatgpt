I audited the current `main` at `e5c4a7c8...`, including the browser/runtime path, consultation engine, tool registration, configuration, response parser, and the prior Round 2 audit fixes. The project is substantially more resilient than the pre-hardening version, but both UX concerns you raised are valid.

My overall assessment is:

**1. Ordinary ChatGPT failures are handled reasonably well; true hangs and truncated streams are not yet contained strongly enough.**
**2. Autonomous adviser use is possible, but absolutely not guaranteed today.** In fact, the documentation correctly says `autoConsult` is currently reserved and has no effect.

| Severity  | Finding                                                    | Practical effect                                                                   |
| --------- | ---------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| **P1**    | Browser transaction/driver queues have no deadman lease    | One genuinely hung browser promise can block every later consultation indefinitely |
| **P1**    | Partial stream can be mistaken for completed advice        | A stopped/truncated ChatGPT answer may be accepted as successful                   |
| **P1**    | Pi tool cancellation signal is discarded                   | Aborting the agent/tool call does not necessarily abort the consultation           |
| **P1 UX** | No deterministic agent-use policy                          | “Use ChatGPT as adviser” does not guarantee a tool call                            |
| **P1 UX** | Async result delivery is human-facing, not worker-facing   | Adviser may finish but the agent never consumes the advice                         |
| **P2**    | No inactivity/stall watchdog                               | A visibly stuck generation can consume the full 4-minute timeout                   |
| **P2 UX** | Tool progress callback is unused                           | A long consultation can look frozen                                                |
| **P2 UX** | Eight low-level tools increase routing/choreography burden | Smaller worker models are more likely to omit or misuse the adviser workflow       |

## 1. Failure resilience: good foundation, but one important hole

The current implementation already has several mechanisms I would keep. Every job is persisted before browser work, the engine has consultation-scoped `AbortController`s, cancellation is durable, stale `running` jobs are reconciled after restart, browser generations have a configured deadline, and timeout/cancellation resets the tracked tab so a previous stream cannot contaminate the next consultation.

So a normal case like:

> ChatGPT keeps showing “generating” forever, but the browser remains responsive

is already bounded. The default is four minutes, after which the driver resets the tab and returns `generation-timeout`.

The harder case is different:

> a Playwright operation, Chrome renderer call, DOM probe, or some other awaited promise itself never settles.

The process-wide browser transaction scheduler is essentially:

```text
await previous
try:
    await operation()
finally:
    release()
```

with no lease or outer watchdog. The driver's own `runExclusive()` uses the same general promise-tail pattern. If `operation()` never reaches its `finally`, its successors wait indefinitely.

That matters because the generation deadline is **inside** `askAndAwaitTurn()`. If execution hangs on one `await this.#snapshot()`, a browser call, conversation navigation, etc., control never returns to the code that checks `Date.now() < deadline`.

This is the remaining true-deadlock class I would treat as P1.

### The cancellation path has the same edge case

Explicit `/advisor-cancel` is now much better: the engine aborts the consultation, the driver observes the signal between polling/browser operations, and a touched turn resets the tab. That's a legitimate improvement over your previous audit.

But if the active browser call itself is hung, the signal cannot be observed until that call returns.

There is also a separate wiring bug: Pi gives each agent tool an `AbortSignal`, and your engine accepts `request.signal`, but `advisor_submit` receives it as `_signal` and never passes it to `submitSync()`/`submitAsync()`. `advisor_followup` does the same.

So these currently differ:

```text
agent calls advisor_submit
user/agent aborts the Pi tool call
    → signal discarded

agent calls advisor_cancel explicitly
    → engine AbortController actually fires
```

That should be fixed irrespective of the deeper browser watchdog.

## 2. Interrupted streaming can currently produce a false success

This one is subtler and directly matches your “streaming stopped before completion” example.

The current turn classifier essentially declares success when:

```text
we sent the message
AND our user message appeared
AND generation indicator disappeared
AND a new assistant message exists
```

It does not prove that ChatGPT actually finished the logical response.

Imagine ChatGPT produces:

```text
consultation: adv-123
reviewed_commit: abcdef...
status: actionable

## ASSESSMENT
I found three important problems...

## RECOMMENDATION
The first thing I would...
```

and then the stream disconnects. If the stop/generating affordance disappears and no recognized error banner remains, that partial assistant node can satisfy `classifyTurn() === "complete"`.

The response parser will not catch this reliably. Its philosophy is intentionally permissive—minor structural deviations do not fail the consultation—and there is no end-of-response marker. If the ID and SHA occurred near the beginning, the truncated response can even receive `resultStatus: "complete"`.

I would add a **completion sentinel** to the adviser protocol. For example, require the final line to contain something equivalent to:

```text
consultation_complete: adv-123
```

Then distinguish:

```text
DOM transport complete + valid terminal marker → complete
DOM transport complete + marker absent         → incomplete-response
generation still active                        → generating
browser inactivity                              → stalled
absolute deadline                               → timed-out
```

This is much more reliable than trying to enumerate every ChatGPT UI manifestation of “stream disconnected before completion.”

An incomplete response could be retained for diagnostics, but should **not** become normal actionable advice automatically.

## 3. Add two timeouts, not one

I would change the current single timeout concept into two independent guardrails.

A **hard operation deadline** bounds the entire consultation transaction: capability verification, Project selection, conversation selection, model selection, submission, generation, receipt, and persistence. This needs to sit *outside* the browser transaction, not merely inside the generation polling loop.

A **stall deadline** should be much shorter and reset whenever meaningful progress occurs. For example, 30–60 seconds with no change in assistant output/generation state could classify the turn as `stalled`, while the hard maximum could remain around four minutes.

The important implementation detail is that timeout recovery needs an **out-of-band browser interrupt**. Calling another operation through the same locked queue cannot recover the lock that is already stuck.

I would give the browser owner something conceptually like:

```text
normal transaction
    ↓ exceeds lease
invalidate browser generation/epoch
    ↓
force-close BrowserContext outside normal transaction queue
    ↓
pending Playwright operations reject
    ↓
mark job stalled/interrupted
    ↓
construct fresh tab/context
```

Do not merely release the mutex while the old operation continues; that would recreate the cross-conversation races you worked hard to remove.

If you eventually want extremely strong containment, moving the Playwright adviser runtime into a small child process gives you the cleanest ultimate deadman switch: kill and recreate the process. I would not require that for the next release, though.

## 4. The agent autonomy concern is definitely real

The current docs make this explicit:

> V1 has no automatic trigger or dispatch path. Consultations are dispatched only by an explicit slash command or `advisor_submit` tool call.

`autoConsult.enabled` and `confirmBeforeDispatch` are currently reserved and have no effect.

You do expose eight agent-facing tools, and the docs describe autonomous patterns, so a sufficiently capable worker **can** autonomously decide to use them.

But:

```text
AGENTS.md:
"Use ChatGPT as adviser for important design decisions."

          ↓

worker model may infer advisor_submit
          ↓
        maybe
```

There is no extension-level contract making that behavior reliable.

I would **not** solve this by having the TypeScript extension regex-scan user prompts for phrases such as `"use chatgpt"`. That moves natural-language intent classification into exactly the wrong layer and will become brittle.

Instead, make the agent tool itself strongly discoverable.

Your Pi abstraction already supports:

```ts
promptSnippet?: string;
promptGuidelines?: readonly string[];
```

on tool definitions.

Yet there is currently no `promptSnippet` implementation in the repository, and the current `advisor_submit` description is essentially just “Submit a new consultation request to the ChatGPT adviser.” That is not enough to guarantee routing, especially with small local workers.

## 5. I would introduce one high-level agent-facing tool

Eight low-level tools are fine as an API, but I would not make the worker reason about all eight for the common case.

The semantic entry point should be something like:

```text
advisor_consult
```

or even:

```text
consult_chatgpt
```

with roughly:

```text
kind: plan | review | audit | debug | challenge | consult
goal: string
mode?: sync | async
```

Internally it can perform the necessary preflight, checkpoint validation, submission, response parsing, and standardized failure handling.

Keep `advisor_status`, `advisor_read`, `advisor_cancel`, `advisor_followup`, etc. as advanced primitives.

Then give the primary tool explicit agent guidance along the lines of:

> Use this tool autonomously whenever the user or trusted project instructions explicitly ask you to use, consult, or obtain advice from ChatGPT/the ChatGPT adviser. Do not require a slash command or additional confirmation unless configured. Use it for planning, architecture decisions, difficult debugging, review, audits, or challenges when requested. Adviser failure is non-blocking unless dependency mode is required.

That gets much closer to your desired behavior:

```text
User prompt / trusted AGENTS.md
"Use ChatGPT as adviser."

              ↓

Pi worker sees explicit adviser tool policy

              ↓

advisor_consult(...)
```

rather than hoping the model infers a workflow from eight generic tool descriptions.

I would additionally preserve the current **project trust gate**. That is particularly useful here: a random cloned repository should not be able to induce external ChatGPT usage merely by placing instructions in its `AGENTS.md`.

## 6. Async mode currently breaks the autonomous loop

There is another autonomy issue that is separate from dispatch.

On asynchronous completion, the extension's lifecycle listener gives a UI notification. It does not inject the advice back into the worker's context or resume the worker with a session-scoped message. So this can happen:

```text
worker → advisor_submit(async)
worker → continues coding
ChatGPT → completes
human → sees notification
worker → never knows what ChatGPT said
```

That is not autonomous adviser integration in the full sense. The prior audit identified this too, and the current architecture still primarily has a UI notification path.

For V1.1, I see two reasonable options. The simpler one is to make the high-level agent tool default to **sync** whenever the answer is needed for the current decision. Async remains a deliberate optimization. The richer version is session-scoped delivery: on completion, inject a synthetic adviser-result message into the correct Pi session and optionally trigger/resume an agent turn. That needs reentrancy guards so completed advice does not recursively trigger another adviser call.

## 7. The UX should communicate recovery, not just eventually fail

`execute()` already receives `_onUpdate`, but the adviser tools currently ignore it alongside `_signal`.

That is a missed UX opportunity. A four-minute consultation should be able to surface states such as:

```text
Verifying GitHub checkpoint…
Opening adviser conversation…
ChatGPT is reasoning…
No output progress for 35s; checking adviser health…
Adviser stream appears incomplete; discarding partial result…
ChatGPT unavailable; continuing locally.
```

This both makes real waits feel intentional and makes actual failures diagnosable.

### What I would implement next

In priority order:

1. **Bound the whole browser transaction**, with a watchdog capable of force-invalidating/closing the browser outside the normal lock; add a regression where a deliberately never-resolving driver call cannot permanently block consultation B.
2. **Add response-completion provenance**, preferably a final consultation-ID sentinel, and classify missing-sentinel answers as `incomplete-response`, not success.
3. **Wire Pi's `signal` and `onUpdate` through** `advisor_submit` and `advisor_followup`; cancellation must propagate from the original tool call.
4. **Add stall detection** separately from the absolute deadline, plus a small circuit breaker after repeated browser/provider failures.
5. **Create `advisor_consult` as the primary semantic agent tool** and attach strong `promptSnippet`/`promptGuidelines`; specifically name the trigger “when user or trusted AGENTS/project instructions say to use ChatGPT as adviser.”
6. **Make the currently reserved autonomy setting real**, probably renamed from vague `autoConsult` to something like `agentUse`, with a global user-controlled enable/confirmation policy.
7. **Close the async delivery loop** by either making agent consultations sync by default or delivering completed advice back into the originating Pi session automatically.
8. Add behavioral evaluations using the actual worker classes you care about: a small local Qwen-class model and Luna-class inexpensive cloud worker. Give them prompts such as “use ChatGPT as adviser,” “get a second opinion from ChatGPT after implementation,” and “do this yourself, no adviser,” and verify respectively **call / call-at-checkpoint / do-not-call** behavior.

The architecture is already quite close. I would treat the next work as a focused **“resilient autonomous adviser UX”** slice rather than another broad refactor. The key conceptual change is that the extension needs both **failure containment at the outermost browser boundary** and an explicit **agent-routing contract at the innermost worker-facing boundary**. Those are the two layers currently missing.
